# 插入性能优化方案

状态：**方案 A（`putAll` 批量化）已实施**（提交 f409d9f，README 9.4 批量档 + 用例 C13 落地，实测批量插入 12×）。方案 B（单文件布局）留作下一大版本；方案 C（组提交）不做。以下保留原始分析与取舍记录。
基线：README 9.4（fsync 全开，100 万条，Windows + NVMe SSD）——插入 905 ops/s、p50 1,003 µs。

---

## 一、瓶颈定位（实测拆解，不是推测）

用一段独立微基准（`build/FsyncProbe.java`，临时脚本，不入库）复现组件插入路径的**完全相同 I/O 模式**：追加 ~600 B 记录 → 写 16 B 槽位 → 写 64 B 文件头，只改变持久化强度。同一块 NVMe、同机、`-Xmx256m`：

| 模式 | 吞吐 | 平均延迟 | 相对逐写 2 fsync |
|---|---|---|---|
| A 纯 I/O，无 fsync | 29,370 ops/s | 34.0 µs | 34.3× |
| B 每写 1 个 fsync | 1,675 ops/s | 597 µs | 2.0× |
| **C 每写 2 个 fsync（现状）** | **857 ops/s** | **1,167 µs** | 1× |
| D 批量：N 次写之后各 1 次 fsync | 18,512 ops/s | 54.0 µs | **21.6×** |

推导：
- 单个 `force` 实测成本 ≈ **563 µs**（B−A），第二个 ≈ **570 µs**（C−B），两者线性叠加。
- 组件实测插入 p50 = 1,003 µs，与 C 的 1,167 µs 吻合（组件多了哈希与字符串编码，量级一致）。
- 全部结构层工作（哈希、探测、追加记录、写槽位、写头、页缓存往返）合计 **34 µs，占 2.9%**。

**结论**：插入性能 97% 花在两次 `FileChannel.force` 上。哈希结构、文件布局、系统调用次数、缓存策略**都不是瓶颈**——A 模式的 29,370 ops/s 就是当前结构的天花板，任何不涉及 fsync 次数的优化，收益上限只有 3%。

因此可选方案只有三类：**摊薄** fsync（多次逻辑写共享一次）、**减少** fsync（每次逻辑写只剩一个）、**移走** fsync（异步化，改变语义）。

## 二、方案清单

### 方案 A：`putAll` 批量化（推荐，性价比最高）

**现状**：`putAll`（FileBackedMap.java:1511）是 `for (entry : m) put(k, v)`，每条继承单条写的 2 个 fsync。批量导入 100 万条 = 200 万次 `force`。

**做法**：在**一次**写锁内完成整批
1. 逐条：探测槽位 → `appendRecord` → `writeSlot`（复用单键 put 的墓碑复用与链式探测逻辑）
2. 全程**不做 `force`、不做 `maintain`**
3. 批次结束：`writeHeader()` → `data.force(false)` → `index.force(false)` → 调用**一次** `maintain()`

**预期**：批量写入 ~18,500 ops/s（**21.6×**，D 模式实测）。`putAll(1M)` 从约 18 分钟降到约 54 秒。

**为什么安全（逐条对照现有不变量）**
- 「先写记录字节，再发布槽位」：批次内每条仍是 `appendRecord` 先于 `writeSlot`，顺序未变。
- 「游标 = 文件长度」：批次内多次追加依次推进 `dataEnd`，不覆盖任何被槽位引用的活记录。
- 崩溃落在批次中间：槽位与头留在页缓存未落盘 → 下次打开脏标记（bit0，打开时已 fsync 落盘）触发**既有对账**：重算 entryCount / tombstone / garbage、丢弃指向越界偏移的悬空槽位。表现是「批次部分生效」——与 `Map.putAll` 契约兼容（`HashMap.putAll` 同样不保证原子）。
- `maintain()` 延后到批次结束：中途负载率超过 2/3（`overloaded()`，:1101）时，批次内后续键的探测链会变长（性能退化），但正确性不受影响——批次结束后扩容/整理照常触发。
- 公开 API 面不变（`putAll` 本就是 `Map` 接口方法）；单键 `put` 的逐写落盘语义不变。

**改动量**：约 40 行（把 `put` 主体抽成 `putLocked(k, v, boolean allowMaintain)`，`putAll` 循环调用后统一收尾；`allowMaintain` 参数已存在于内部签名）+ README 第九节与第十节各一处。

**顺带受益**：`replaceAll`、崩溃对账（已是批量 force）、`clear()` 走的都是复合路径，同一批量化模式可复用。

### 方案 B：单文件布局（结构性，收益 2×，工作量大）

把索引与数据合并为一个文件（索引头 + 槽位区 + 追加记录区，`dataEnd` 变成文件内偏移）。索引槽位与它指向的记录落在**同一个 `FileChannel`**，逐写持久化从 2 个 fsync 降到 **1 个** → 插入约 1,675 ops/s（**2.0×**）。

**附带收益**（这才是 B 真正的价值）：
- 提交线从六步缩成单点提交——「写完整新文件 → fsync → 改名」。W1/W2/D1/D2/R1/R2 与「原始对齐全 / tmp 对齐全」两条恢复规则塌缩成「新旧两个文件，新文件存在且 CRC 有效即已提交」，5.2 与 5.5 整节可缩短。
- 少一次 `force`、少一个文件句柄、少一类跨文件一致性推理。

**代价**：文件格式升级到 v5（`FORMAT_VERSION`，CRC span 变）、`rebuild`/`growIndex`/对账/恢复全部重写、全部 12 个崩溃用例重建、老文件需要迁移路径。**建议作为独立大版本立项**，不与 A 混做。

### 方案 C：组提交（吞吐最高，破坏语义）

后台 flusher 线程 + 提交队列：`put` 把写请求入队并返回，flusher 每 K 毫秒合并一批做 2 个 fsync。上限 = A 模式的 29,370 ops/s（**34×**）。

**代价**：直接违反现有「`put` 返回即落盘」承诺，必须新增 API 表达（如 `putAsync` + `flushPending()` + 可等待的提交句柄），并发协议要重做（读线程可能读到未提交槽位），崩溃语义需要重新定义。与组件「刻意只做崩溃安全」的定位冲突，**不建议**。

### 方案 D：不改代码，只在文档给出批量导入配方

`putAll` 批量化（A）之前，用户可自行分块调用现有 API 得到部分收益；把这一点写进 README 即为 D。零风险、零收益。

## 四、A 的验收清单

| 项 | 验收标准 |
|---|---|
| 功能 | `putAll` 与逐条 `put` 结果逐键一致（含 null 值、空串、已存在键覆盖、墓碑复用）；`size()` / `hashCode()` / 迭代顺序语义不变 |
| 崩溃 | 新增用例：`putAll` 中途强杀进程 → 重开触发对账，`size()` 与槽位扫描自洽、无悬空槽位、无「槽位指向未落盘偏移」；对账后所有键值可读且等于已落盘内容 |
| 维护 | 批次跨越 2/3 负载阈值 → 结束后扩容/整理正常触发，索引自洽（重放全部键可查） |
| 性能 | `Benchmark` 增加批量模式（`putAll` 每 1,000 条一批）：插入吞吐相对 905 ops/s 提升 ≥ 10×；单键 `put` 吞吐不回退（仍 ~905 ops/s） |
| 并发 | 复用 `ConcurrencyTest`：`putAll` 整体在写锁内，回调重入与 fail-fast 语义不变 |
| API 面 | `javap` 公开面不变（两构造器 → 一个构造器 + Map @Override + close） |
| 文档 | README 9.4 / 9.10 复现命令 / 第十节同步；本文档在 A 实施后删除或标记为「已实施」 |

## 五、被排除的方向（供后续提问时直接引用）

| 方向 | 为什么不选 |
|---|---|
| 索引区改 mmap | 结构层只占 34 µs，省掉页缓存往返最多赚 30 µs（3%）；`force` 成本不变，反而失去显式 I/O 的可控性 |
| 缓存槽位 / 内存哈希目录 | 同上，上限 3%；且引入「内存目录与磁盘槽位」双份真相，破坏恢复的唯一性 |
| 减少 `writeHeader` 次数 | 头写在页缓存里（无 fsync），成本已在 34 µs 内 |
| 原地覆盖记录（免追加） | 消除写放大只影响**整理**耗时（19.7 s），插入路径本来就是追加一次；且撕裂记录会摧毁崩溃安全 |
| 调低负载因子 / 调大桶 | 平均探测次数已接近 1，无空间 |
| 换 `FileChannelImpl` 直写 / DirectBuffer | 影响的是带宽，写入量小（600 B），瓶颈是同步往返不是带宽 |

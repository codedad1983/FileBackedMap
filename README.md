# FileBackedMap —— 基于文件存储的 Java Map 组件

一个 `Map<String, String>` 的实现，**数据全部保存在磁盘文件里，不驻留内存，也不使用内存映射**。对外 API 与 `java.util.HashMap` 完全一致，可以直接替换使用。

槽位（索引）与数据（记录）分别放在两个文件里：**扩容只重建 32 MB 级索引，数据区一字节都不动**。

- 仓库：<https://github.com/codedad1983/FileBackedMap>
- 发布页：<https://github.com/codedad1983/FileBackedMap/releases>（推送 `v*` 标签自动构建发布 `filebackedmap-<版本>.jar` 与 `-sources.jar`）
- 坐标：`com.codedad:filebackedmap:0.0.1`（Java 17+；生产代码零第三方依赖，测试用 JUnit 5）

## 一、需求对照

| 要求 | 实现方式 |
|---|---|
| 功能与内置 Map 一致 | `implements java.util.Map<String, String>`，实现了 `put/get/remove/clear/putAll/size/containsKey/containsValue/keySet/values/entrySet/forEach/replaceAll/putIfAbsent/replace/compute/computeIfAbsent/computeIfPresent/merge/equals/hashCode`，语义与 `HashMap` 一致（含 null 键、null 值、空串，非 String 入参按“不存在”处理） |
| 数据不保存在内存中 | 进程内只保留 7 个数字（槽位数、条目数、墓碑数、数据区终点、垃圾字节数、flags、modCount）。每次 `get/put/remove/遍历` 都用 `FileChannel.read(ByteBuffer, long)` / `write(ByteBuffer, long)` 做定长定位读写；内存里只有单条记录解码后的临时 String 与复用缓冲 |
| 通过文件读写存取 | **两个普通文件**：索引文件 `<path>`（头 + 槽位区）与数据文件 `<path>.data`（只追加的记录区，固定名，永不改名） |
| 不使用内存映射 | 没有 `FileChannel.map`、`MappedByteBuffer`，也没有一次性把文件读进堆 |
| 键值都是 String，长度不固定、无限制 | 记录编码为 `[int len][UTF-8 bytes]`，`-1` 表示 null。任意字符（中文、emoji、控制字符）与任意长度都支持（单条记录上限约 2 GB，总容量只受磁盘限制） |

## 二、两个文件各包含什么信息

组件把「哈希表结构」和「键值内容」彻底分开，各存一个文件。两个文件是**一组**：索引文件 `<path>` 与数据文件 `<path>.data` 必须同时存在、一起备份。

### 2.1 索引文件 `<path>` —— 哈希表本体（不含任何键值内容）

文件长度固定为 `64 + slotCount × 16` 字节，全部由头 + 槽位构成，没有别的区段。

**64 字节文件头**（写入时按绝对偏移定位，读取时一次性读 64 B）：

| 偏移 | 宽度 | 字段 | 含义 |
|---|---|---|---|
| 0 | 4 B | `MAGIC` = `"FBMP"` | 格式标识，用于识别这不是随便一个文件 |
| 4 | 4 B | `FORMAT_VERSION` = `4` | 格式版本号，打开时校验，不匹配直接拒绝 |
| 8 | 4 B | `slotCount` | 槽位总数，必须是 2 的幂且 ≥ 8，用于 `hash & (slotCount-1)` |
| 12 | 4 B | `entryCount` | 当前键值对数量，`size()` 直接返回它，不需扫描文件 |
| 16 | 4 B | `tombstoneCount` | 墓碑槽数量（已删除、尚未重建的槽） |
| 20 | 4 B | `flags` | bit0 = **脏标记**：会话打开时置 1，正常 `close()` 清零。置位表示「上次未正常关闭，或某次多步更新未完成提交」，打开时需要对账修复 |
| 24 | 8 B | `dataEnd` | 数据区逻辑终点。**打开时一律以数据文件的实际长度为准**，此字段只是缓存值（正因为如此，游标永远不会倒退，也就不会覆盖仍被槽位引用的活记录） |
| 32 | 8 B | `garbageBytes` | 数据区中**不再被任何槽位引用**的字节数（已删除的记录 + 被新版本替换掉的旧记录） |
| 40 | 4 B | `crc32` | 文件头 CRC32，覆盖 0..39 字节 |
| 44–63 | 20 B | 保留 | 未使用，写入为 0（为后续扩展留白） |

**槽位区**：紧接文件头，从偏移 64 开始，`slotCount` 个定长 16 B 槽位，顺序排列。每个槽位内部结构：

| 槽内偏移 | 宽度 | 字段 | 含义 |
|---|---|---|---|
| 0 | 1 B | `state` | `0=EMPTY`（空槽）／`1=OCCUPIED`（占用）／`2=TOMBSTONE`（墓碑） |
| 1–3 | 3 B | 填充 | 未使用（对齐到 4 B 边界，也为将来扩展留白） |
| 4 | 4 B | `hash` | 键的 32 位稳定哈希；用于定位与快速筛选，**不随进程变化** |
| 8 | 8 B | `offset` | 该键值记录在**数据文件**中的起始字节偏移（不是索引文件内的偏移） |

索引文件里**没有键、没有值、没有指针表**，只有这三样：状态、哈希、数据偏移。所以 100 万条目时索引只有 32 MB，而数据可以是 2 GB —— 索引大小只跟槽位数有关，与键值长度无关。

一个关键细节：槽位存的是**数据文件内偏移**。因此扩容时槽位重新分配到新槽位数组，但 `offset` 原样保留，数据文件一个字节都不用改。

### 2.2 数据文件 `<path>.data` —— 只追加的记录区（无文件头）

数据文件**没有任何头字段**，偏移 0 就是第一条记录的开始。文件名固定为 `<path>.data`，**永不改名**；重建过程中的新版本先写到临时文件 `<path>.data.tmp`，提交时改名覆盖固定名。因此稳态下同一时刻只有一个数据文件在服务，崩溃时最多额外留下临时文件，命名不产生歧义。

每条记录是**自描述**的、变长的：

```
[4 B keyLen][keyLen 个字节的 UTF-8 键][4 B valLen][valLen 个字节的 UTF-8 值]
```

信息要素与编码规则：

| 要素 | 编码 |
|---|---|
| 键长度 | `int keyLen`，`-1` 表示 **null 键**（此时没有键字节） |
| 键内容 | 紧随其后的 `keyLen` 个 UTF-8 字节，不做长度上限（仅受单记录 ≤ 2 GB 限制） |
| 值长度 | `int valLen`，`-1` 表示 **null 值**；`0` 表示**空串**（合法值，与 null 区分） |
| 值内容 | 紧随其后的 `valLen` 个 UTF-8 字节 |
| 记录总长度 | `8 + max(keyLen,0) + max(valLen,0)` 字节 |

由此可以推断出的信息：**每条记录自带键和值，定位后无需回索引查键**；null / 空串 / 超长字符串都被区分表达；每条记录只有 8 B 的字段开销（键值本身之外），**无校验字段、无 ID、无版本号**。记录之间没有分隔符，全靠 `keyLen`/`valLen` 推进读取位置。

**只追加 + 不可变**：新记录总是写到当前文件末尾。删除记录、更新记录都不会修改已有字节 —— 旧记录留在原地成为「垃圾」，由 `garbageBytes` 计数，等整理时再清除。**更新一律追加一条新记录**，因此不存在「同长度值原地覆写」这种会产生半新半旧撕裂记录的路径。所以数据文件的长度始终等于实际写入的最高偏移，但其中可能混有已废弃的记录。

### 2.3 两个文件之间如何对应

- 哈希表本体只存**槽位 → 数据偏移**的映射；
- 键值本体只在数据文件里；
- 索引是「结构」，数据是「内容」。索引可以整体重建而无损内容；数据可以整理压缩而只需重算偏移。

## 三、文件内部数据结构

### 3.1 索引结构 = 一个持久化的开放寻址哈希表

- 槽位数组本身就是哈希表：`slotCount` 个槽，`mask = slotCount - 1`。
- 定位：`idx = hash & mask`，若该槽不是空槽，则 `idx = (idx + 1) & mask` 继续**线性探测**，直到遇到 `EMPTY`。平均 1 次探测，最坏 `slotCount` 次。
- 判断键相等：先比对 `hash`（4 B），只有哈希相同才去数据文件读键字节逐字节比较 —— 避免为每个候选槽解码 String。
- 墓碑：删除时把状态改成 `TOMBSTONE`、偏移置 -1，使探测链不被截断；后续 `put` 在探测路径上优先复用第一个墓碑槽。
- 负载控制：`(entryCount + tombstoneCount) / slotCount ≥ 2/3` 时扩容，扩容后墓碑清零。
- 槽位数始终是 2 的幂（初始 8），保证 `hash & mask` 均匀。

### 3.2 数据区结构 = 无索引的追加日志

- 记录按写入顺序线性排列，不排序、不分组、不建二级索引；
- 一条记录的长度由它自己的 `keyLen`/`valLen` 决定，读取时按这两个长度推进，因此记录之间不需要分隔符；
- 由于值长度可变，记录长度也变；**任何更新都追加新记录**（旧版本成为垃圾），不做原地覆写 —— 这样一条记录要么完整、要么不存在，绝不会出现撕裂；
- 垃圾整理时按槽位顺序流式读取存活记录、连续重写到新数据文件（`<path>.data.tmp`），同步确定每条记录的新偏移并重建索引，最后走固定提交线换版（见 5.2）。

### 3.3 哈希函数

自写的 **MurmurHash3_x86_32 变体**，作用于键的 UTF-8 字节（null 键哈希为 0）。不用 `String.hashCode()` —— 它在不同 JVM/版本下不稳定，而哈希要被持久化，必须跨进程可重现。

## 四、扩容与垃圾整理

| 触发条件 | 动作 | 代价 |
|---|---|---|
| `(条目 + 墓碑) / 槽位数 ≥ 2/3` | `growIndex()`：**只重建索引文件**，`hash`/`offset` 原样搬过去 | 写入 `newSlotCount × 16 B`；100 万条目时约 32 MB。**数据文件不动** |
| `垃圾 > max(4096, 数据区一半)` | `rebuild()`：垃圾压缩，**双文件重建**（记录连续重排 + 偏移重算 + 重算哈希） | 必须重写数据区，这是真正的开销所在（1 GB 数据区实测约 19.6 s） |

- **删除**：槽位置墓碑，数据区对应记录成为垃圾（不立刻重写文件）。
- **更新**：一律追加新记录 + 槽位改写，旧版本成为垃圾。**不原地覆写** —— 保证每条记录完整不可变。
- `growIndex` 与 `rebuild` 的提交方式不同：
  - `growIndex`（扩容）= 只写临时索引 → 重命名索引，**数据文件完全不动**（单次改名即原子提交）；
  - `rebuild`（整理 / 清空）= 走固定六步提交线（见 5.2），换版时索引与数据一起换。
- 搬移过程流式进行，内存里只驻留一条记录（重建槽位表时另持有 13 B/槽位的目标表）。
- 重建采用**块 I/O**：4096 槽位（64 KB）一块读、一块写，而不是逐槽位 16 B 读写 —— 后者会把「32 MB 写入量」变成百万次系统调用（实测慢 105 倍）。

## 五、并发与持久性

### 5.1 并发

- 所有文件操作都在实例级 `synchronized` 内，同一实例多线程共享安全（串行化，等价于同步版 Map）。
- 迭代期间的结构性修改抛 `ConcurrentModificationException`（与 `HashMap` 一致）；迭代器自身的 `remove()` 允许，`entry.setValue()` 也允许（它走「不触发维护」的写入路径，避免迭代途中重建文件）。

### 5.2 落盘顺序：只完成一个文件时会发生什么

双文件设计最怕的是「一个文件已落盘、另一个没有」。如果索引指向的偏移落在旧数据的无关字节上，`get` 会**静默返回错值** —— 这种错误比崩溃更糟，因为它会继续扩散。以下四条不变量把这种情况排除掉：

| # | 不变量 | 崩溃时的后果 |
|---|---|---|
| 1 | **记录不可变**：任何更新都追加一条新记录，绝不原地改字节 | 不存在「半新半旧」的撕裂记录；一条记录要么完整、要么整条不存在 |
| 2 | **先写记录、再发布槽位** | 最坏是「一段孤儿记录、无人引用」 = 垃圾；不会出现槽位指向不存在记录的情况 |
| 3 | **游标以实际文件长度为准**（`dataEnd` 只是缓存，打开时一律用 `data.size()` 校准） | 游标不可能倒退，因此下次追加**永远不会覆盖仍被槽位引用的活记录** |
| 4 | **固定六步提交线**：重建严格按「W1 写 `data.tmp` → W2 写 `index.tmp` → D1 删原索引 → D2 删原数据 → R1 改名索引 → R2 改名数据」执行，每步都是原子操作。数据先写：一次槽位扫描同时完成记录拷贝与新索引的槽位映射，索引落盘只是把内存里的映射写出去，全程只扫描一次槽位区 | 崩溃后的文件集合只有六种，每种都由两条恢复规则唯一判定（见下），**绝不会出现「新索引 + 旧数据」这种偏移错位** |

> **两条恢复规则**（打开时按现场文件组合判定，覆盖六步提交线的全部崩溃快照）：
>
> | 磁盘上存在的文件 | 成因 | 恢复动作 |
> |---|---|---|
> | 原索引 + 原数据（±任意 `.tmp`） | 提交点 D1 之前崩溃 | **回滚**：删掉临时文件，用原始对（临时文件里可能是未应答的写入，绝不采用） |
> | 原数据 + `index.tmp` + `data.tmp` | D1 之后 | **续做**：补齐两个改名 |
> | `index.tmp` + `data.tmp` | D2 之后 | **续做**：补齐两个改名 |
> | 原索引(新) + `data.tmp` | R1 之后 | **续做**：补齐数据改名 |
>
> 提交点在语义上是 **D1（删除原索引）**——那一步之后回滚材料被销毁，只剩「续做」一条路。临时文件对是否可用，靠 `index.tmp` 头的 MAGIC/版本/CRC 与 `data.tmp` 长度 == 头 `dataEnd` 联合校验，损坏则报「无法恢复」而非猜错。扩容（`growIndex`）不涉及数据换版，仍是「写 index.tmp → 改名」的单点提交。

### 5.3 打开时的对账（崩溃恢复）

打开文件时如果发现以下任一情况，就走 `reconcile()`：

- 脏标记 `FLAG_DIRTY` 置位（上次没有正常 `close()`，或 `rebuild` 的中间状态）；
- 文件头 CRC32 与内容不匹配；
- `dataEnd` 与实际数据文件长度不一致。

对账做的事（只丢弃、不重建，避免把错误扩散）：

1. 以数据文件**实际长度**为唯一权威游标；
2. 逐槽位校验：偏移越界、长度字段非法、记录超出文件末尾 → 一律改成墓碑并丢弃（`droppedOnRecovery` 计数）；
3. 重算 `entryCount` / `tombstoneCount` / `garbageBytes`，写回带 CRC 的新文件头。

结果：**读不到的内容一律变成「键不存在」，而不会被读成别的键的值**。正常情况下 `close()` 会清除脏标记，下次打开不做对账（`recoveredFromCrash() == false`）。

### 5.4 fsync 顺序与脏标记

- `durable=true` 时，写操作的顺序是 **data.force → index.force**：索引（指向记录）永远最后落盘，因此不可能出现「索引已持久、记录未持久」的组合。
- 会话打开即把脏标记写入磁盘；`close()` 清除它再落盘。若进程被强杀，标记仍在 → 下次打开对账。
- 内部 `flush()` 在每次需要时把两个文件刷到磁盘（同样 data → index），不对用户暴露。

### 5.5 校验与报错边界

- 打开时校验 MAGIC、格式版本（4）、槽位数（2 的幂且 ≥ 8）；
- 索引长度必须 ≥ `64 + slotCount×16`（槽位区被截断属结构性损坏，直接报错，不做修补）；
- 数据文件 `<path>.data` 必须存在（提交线中断时由 `data.tmp` 改名补上），缺失且无有效 `data.tmp` 则报错 —— 绝不静默退化成空表。
- 打开会先走恢复规则（见 5.2），恢复完成后残留的 `.tmp` 一律清除，只是清理，不影响一致性判断。

```bash

javac -encoding UTF-8 -d build/classes $(find src/main/java -name '*.java')

# 运行演示（会打印堆占用几乎不增长）
```

### 6.3 用 Maven

```bash
mvn test                             # 跑 JUnit 5 测试（正确性 9 例 + 崩溃安全 8 例）
```

## 七、用法

```java
import com.codedad.fbmap.FileBackedMap;

// 对外 API 只有 java.util.Map 接口方法 + close()，其余（文件路径、
// 统计、compact、flush）全部是 private，用户拿到的就是一个纯粹的 Map。
try (FileBackedMap map = new FileBackedMap(Path.of("data", "kv.fbmap"))) {
    map.put("name", "张三");
    map.put("note", "x".repeat(1_000_000));  // 长度不限
    System.out.println(map.get("name"));     // 张三
    System.out.println(map.size());
}

// 关闭后重新打开（甚至换个进程），数据仍在（两个文件要一起保留）
try (FileBackedMap map = new FileBackedMap(Path.of("data", "kv.fbmap"))) {
    System.out.println(map.get("name"));     // 张三
}
```

> 部署/备份时注意：索引文件 `<path>` 与数据文件 `<path>.data` 是一组，**必须一起拷贝**。只拷索引文件（且无中断现场的 `data.tmp`）会在打开时明确报「数据文件缺失」，不会静默给出错误内容。备份请选在无重建进行中时做，或直接拷贝整个目录（含可能的 `.tmp`，组件能自行续做或回滚）。

## 八、测试覆盖

两套测试均为 **JUnit 5** 测试类（`mvn test` 自动执行，合计 21 个 `@Test`；单个用例内是成百上千条对照断言，任何一条不符即失败）。每个用例使用 JUnit `@TempDir` 独享临时目录，用例之间零共享状态。

`FileBackedMapTest`（`com.codedad.fbmap.test`）的 9 个用例（约 5300+ 项断言，与 `HashMap` 逐条对照）：

1. 基本增删改查、size、clear（clear 后索引回到 64 + 8×16 = 192 B，数据文件为空）
2. null 键、null 值、空串、中文、emoji、控制字符，含 null 键/值的各类更新路径
3. 超长键（20 万字符）与超长值（150 万字符 UTF-8），值变短后的更新
4. 关闭重开后数据完整（持久化，索引 + 数据两个文件都能正确校验）
5. 5000 轮随机操作与 `HashMap` 逐条对照（返回值、size、内容、hashCode、keySet、values、entrySet 包含关系）
6. Java 8 默认方法：`putIfAbsent/compute/computeIfAbsent/computeIfPresent/merge/replace/replaceAll/forEach/putAll/remove(k,v)`
7. 迭代器：遍历计数、迭代 `remove()`、`entry.setValue()` 写回、快速失败
8. 视图与 `equals/hashCode/toString`
9. 压力混合（黑盒）：反复改值长度 5 轮造垃圾、驱动内部自动扩容/自动整理，再删 90%、插入 3000 条，内容仍与 HashMap 完全一致（不触碰任何非公开方法）

`CrashSafetyTest`（`com.codedad.fbmap.crash`）的 12 个用例直接改写文件字节 / 摆布文件，构造各种「只完成一个文件落盘」与「提交线各步中断」的状态：

| 用例 | 构造的异常状态 | 期望行为 |
|---|---|---|
| C1 游标落后 | 数据已追加，但头里的 `dataEnd` 比实际文件短 60 B | 对账校准游标；下一次 `put` 追加在末尾，**旧键全部仍正确**（不被覆盖） |
| C2 悬空槽位 | 槽位偏移改到数据文件之外 + 99 万 | 该槽位转墓碑丢弃，`size` 减 1，其余键仍正确；该键变「不存在」而非错值 |
| C3 撕裂记录 | 数据文件末尾被截掉 200 B，但槽位仍指向它 | 不可验证的槽位被丢弃，`get` 返回 `null`，不读出半条数据 |
| C4 CRC 损坏 | 改文件头一个字节但不重算 CRC | 触发对账，计数按槽位重算后仍与真实内容一致 |
| C5 W1/W2 后崩溃 | 双原始都在 + 一份完整有效的 `index.tmp`+`data.tmp`（内容是「清空版」） | **回滚**：删两个 tmp，仍是旧内容，绝不采用未提交的清空版 |
| C6 原数据缺失 | 原索引在、`<path>.data` 被删且无 `data.tmp` | 打开时明确抛 `IOException`，不静默降级 |
| C7 正常关闭 | — | 磁盘上的脏标记被清零，重开 `recoveredFromCrash() == false` |
| C8 重建提交 | `compact()` / `clear()` | 数据文件保持固定名 `.data`、提交后无 `.tmp` 残留、内容仍与 HashMap 一致 |
| C9 D1 后崩溃 | 原数据 + 有效 tmp 对（原索引已删） | **续做**两个改名，采用 tmp 新内容 |
| C10 D2 后崩溃 | 只剩 tmp 对（两原始都删） | **续做**两个改名，回到固定名 |
| C11 R1 后崩溃 | 新索引已转正 + `data.tmp` 未改名 | **续做**数据改名 |
| C12 原始已删 + tmp 损坏 | 只剩损坏 tmp，或新索引缺配套数据 | 无法恢复，明确抛 `IOException` |

### 9.1 测试环境

| 项目 | 值 |
|---|---|
| 操作系统 | Windows（桌面版） |
| CPU | Intel Xeon W-2223 @ 3.60 GHz |
| 内存 | 255.7 GB 物理内存 |

| 磁盘 | C: 盘，剩余约 187 GB（测试文件 2.1 GB 可容纳） |

### 9.2 测试样本

| 项目 | 规格 |
|---|---|
| 键 | `"k<下标>#"` + 随机字符，总长度 **100–1000 字符**随机 |
| 值 | 随机字符，长度 **100–1000 字符**随机 |
| 字符池 | `a-zA-Z0-9-_ .`（纯 ASCII，UTF-8 每字符 1 字节） |
| 总量 | **1,000,000** 条键值对 |
| 样本生成方式 | 确定性：由下标推导 key、由种子推导 value，**不保存在内存中** |
| 样本原始负载 | 键 + 值合计 **1,048 MB**（UTF-8 原始字节） |

> 之所以用确定性生成：如果预先构造 100 万个 String 并留在内存里，测的就不是「数据不在内存」的组件，而是内存中的字符串开销。这样每个操作只付出真实解码一条记录的成本。

### 9.3 测试流程

1. **插入**：100 万次 `put`，键 `keyFor(i)`，值 `valueFor(SEED_INSERT, i)`
2. **修改**：100 万次随机键的 `put`（值换成另一组随机值），随机键由 `Random(0x5DEECE66D)` 选出，**全部命中已存在的键**
3. **查找**：100 万次随机键的 `get`，随机键由 `Random(0xDEADBEEF)` 选出

每个操作单独计时（`System.nanoTime()`），统计平均、p50、p95、p99、p999 与最大值；后台线程每 20 ms 采样堆占用峰值。

### 9.4 吞吐与延迟

| 阶段 | 次数 | 总耗时 | **吞吐（次/秒）** | 平均延迟 | p50 | p95 | p99 | p99.9 | 最大值 |
|---|---|---|---|---|---|---|---|---|---|
| **插入** | 1,000,000 | 42.887 s | **23,317 ops/s** | 42.89 µs | 25.70 µs | 60.30 µs | 103.40 µs | 208.90 µs | 53.5 ms |
| **修改** | 1,000,000 | 92.285 s | **10,836 ops/s** | 92.28 µs | 49.60 µs | 84.40 µs | 127.30 µs | 259.50 µs | 25.4 s |
| **查找** | 1,000,000 | 48.421 s | **20,652 ops/s** | 48.42 µs | 37.50 µs | 63.90 µs | 90.70 µs | 208.60 µs | 35.7 ms |

命中率：修改 1,000,000 / 1,000,000 全部命中已存在键；查找 1,000,000 / 1,000,000 全部命中。

按 p50 折算的稳态瞬时吞吐（平均值与 p50 的差异来自 4 次扩容重建、1 次垃圾整理与少量长尾）：

| 阶段 | 稳态瞬时吞吐（按 p50） |
|---|---|
| 插入 | ≈ 38,900 ops/s（25.7 µs） |
| 修改 | ≈ 20,200 ops/s（49.6 µs） |
| 查找 | ≈ 26,700 ops/s（37.5 µs） |

> 修改阶段末尾那次 **25.4 s** 的 `max` 是自动垃圾整理（`rebuild`）：100 万次更新全部是「追加新记录」，垃圾字节恰好越过「数据区一半 / 4096」门槛，于是整条数据区被重写一遍。这是策略的必然结果 —— 更安全（记录不可变）的代价是更高的写放大。整理本身单独实测为 19.6 s（见 9.6）。

### 9.5 与 HashMap 对照（同样 100 万条、同样样本）

| 阶段 | FileBackedMap | HashMap | 倍数（HashMap / 本组件） |
|---|---|---|---|
| 插入 | 23,317 ops/s | 77,056 ops/s | **3.3 倍** |
| 修改 | 10,836 ops/s | 74,594 ops/s | **6.9 倍**（含一次整理；剔除整理后约 5.0 倍） |
| 查找 | 20,652 ops/s | 148,019 ops/s | **7.2 倍** |
| 堆占用 | 约 9 MB（峰值 96 MB，含测试数组与扩容重建表） | **1,184 MB** | 内存差约 130 倍 |

> HashMap 的 1,184 MB 含 100 万条 key/value 的字符串对象与节点开销（原始负载 1,048 MB）。

### 9.6 磁盘使用量（双文件口径）

| 时点 | 索引文件 | 数据文件 | 合计 |
|---|---|---|---|
| 插入完成后 | 33,554,496 B（32.0 MB） | 1,107,581,914 B（1,056.3 MB） | **1,088.3 MB** |
| 修改完成后（最终保留状态） | 33,554,496 B（32.0 MB） | 1,107,739,919 B（1,056.4 MB） | **1,088.4 MB** |
| 手动 `compact()` / 自动整理后（另测，未保留） | 33,554,496 B（32.0 MB） | 1,107,438,410 B | **1,088 MB**（整理耗时 19.6 s） |

- **索引只占 3%**：32 MB 索引 vs 1,056 MB 数据 —— 这正是拆分的目的，扩容只需动这 32 MB。
- **编码开销极小**：原始 key+value 负载 1,048 MB，数据区 1,056.3 MB，每条记录仅 8 B 头 —— 额外开销 **0.76%**。
- **修改后文件没有翻倍**：因为垃圾门槛（数据区一半）在 100 万次修改的最后被触发，整理已经把垃圾清掉，最终数据区回到 1,056.4 MB。**如果关掉自动整理**，同流程会留下约 2,111 MB（写放大接近 1 倍）—— 这是「用磁盘空间换崩溃安全」的直接体现。
- 最终垃圾仅 **409,182 B**（整理后那一轮的少量残留），已低于门槛。

**文件保留情况**：基准跑完后 `build/bench-data/` 下保留 `fbmap-1M.fbmap`（索引）+ `fbmap-1M.fbmap.data`（数据，固定名）。重开用 `VerifyFinal` 验证：`size() = 1,000,000`，随机抽样查找全部命中、无误值。

> 数据文件名固定为 `.data`：提交线用固定名 + 临时文件，稳态无 `.tmp` 残留。备份时把索引与 `.data` 一起拷即可。

### 9.7 内存使用量

| 指标 | 数值 | 说明 |
|---|---|---|
| 起始堆占用 | 9 MB | JVM 基础开销 + 测试用 8 MB 延迟数组 |
| 插入阶段堆峰值 | 58 MB | 峰值来自扩容重建时的目标槽位表（4,194,304 × 13 B ≈ 52 MB） |
| 修改 / 查找阶段堆峰值 | 96 MB | 采样保留全局最大值（含整理时的一次记录缓冲与临时数组） |
| 结束后堆占用 | **9 MB（delta 0 MB）** | 100 万条数据完全不在堆内 |
| 进程峰值 RSS | 约 90 MB | Windows 工作集，含 JVM 自身 |
| 组件常驻内存 | ≈ 160 B | 槽位数 / 条目数 / 墓碑数 / dataEnd / garbage / flags / modCount + 3 个复用缓冲 |

关键结论：**堆增量 0 MB**。1.04 GB 的键值数据全部在磁盘上，进程只持有头字段与单条记录解码时的临时 `byte[]`。

> 代价说明：扩容重建会临时分配 13 B/槽位的目标表（约 52 MB），换来 105 倍的扩容速度，重建结束后即被 GC 回收。

### 9.8 扩容专项实测

在已有 100 万条的文件上继续插入，直到负载触发扩容：

```
扩容前: slots=2,097,152  index=33,554,496 B (32 MB)
扩容后: slots=4,194,304  index=67,108,928 B (64 MB)
索引重写字节数 = 33,554,432 B (32 MB)
触发扩容的那一次 put 耗时 = 0.238 s   → 索引重写吞吐 134 MB/s
扩容期间数据文件增长 = 441,023,750 B  (只是本轮新增的 398,102 条记录，没有任何搬移/重写)
数据区总大小 = 1,548,763,669 B (1,477 MB)，扩容全程未被重写
扩容后抽样查找命中 = 300 / 300，size = 1,398,102
```

对比「逐槽位 16 B 读写」的实现方式：同样 32 MB 写入量耗时 **24.6 s**（有效吞吐仅 1.3 MB/s），因为 200 万槽位意味着百万次系统调用。改为块 I/O 后耗时 0.238 s —— **成本不是字节数，而是系统调用次数**。

### 9.9 为什么各阶段延迟是这样

- **插入**：命中空槽即停止探测，多数键是新的；p50 25.7 µs 基本是「1 次槽位读 + 1 次记录追加 + 1 次头写」的固定成本。
- **修改**：必须走完探测链（读槽 → 比对 key → 读旧值 → 判是否相等 → 追加新记录 → 写槽 → 写头），且**无论如何都要追加**（不原地覆盖），写放大接近 1 倍；p50 49.6 µs 约为插入的两倍。因为追加使垃圾持续增长，修改阶段末会命中一次 `rebuild`（25.4 s），把平均值拉高到 92 µs。
- **查找**：p50 37.5 µs ≈ 1 次槽位读 + 1 次 key 比对 + 1 次值读（3 次定位 I/O）。这是「系统调用 + 页缓存往返」的固定成本，不是哈希结构问题 —— 开放寻址平均只需 1 次探测。

## 十、已知取舍

- **每次操作都是文件 I/O**：`get` 一次约 2–3 次定位读取，比 HashMap 慢 3.3–7.2 倍（p50 约 37 µs vs 微秒级）。这是“数据不驻内存”的必然代价。
- **更新一律追加 → 写放大 1 倍**：这是为了换取崩溃安全（记录不可变、无撕裂记录）。代价是高频更新会持续产生垃圾，垃圾超过数据区一半时自动触发整条数据区重写（1 GB 实测 19.6 s）。整理是组件内部职责（`private`），无需也不允许外部干预。
- **扩容便宜、整理昂贵**：扩容只重写 32 MB 级索引（实测 0.238 s）；整理必须重写数据区。成本差别来自「写字节数」而非「系统调用」。
- **无缓存**：如需高性能，可在应用层加只读缓存副本（那就等于把数据放回内存，与需求冲突）。
- **单实例独占一组文件**：不支持多进程同时写同一组文件（没有跨进程锁）；只读并发打开也未加锁。崩溃安全只针对**单进程**异常终止，不对并发写负责。
- **不保证迭代顺序稳定**：与 `HashMap` 一样是任意顺序。
- **两个文件必须配对**：索引 `<path>` 与数据文件 `<path>.data` 要一起备份；只拷索引会在打开时报「数据文件缺失」。
- **对账的边界**：对账能保证「不返回错值」，但不保证「不丢已写入的键」。悬空/损坏的槽位会被转成墓碑，表现为该键不存在；若需要更强的保证，请用 `durable=true` 并接受每次写操作两个 fsync 的开销。
- **提交中断只留临时文件**：重建在 D1 之后崩溃会留下 `.index.tmp` / `.data.tmp`，下次打开由两条恢复规则自动续做或回滚，无需人工干预。
